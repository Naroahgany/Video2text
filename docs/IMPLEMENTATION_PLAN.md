# 实施计划

本文档根据 `docs/PROJECT_REQUIREMENTS.md` 中的真实需求拆分开发阶段。当前仍处于文档与计划阶段，暂不实现业务代码。

## 项目定位

目标是实现一个可部署到 Render 的 B站视频转文字小型 Workflow / 小型 Agent 项目。

核心形态：

- 后端：Python FastAPI。
- 前端：原生 HTML/CSS/JS，阶段 1 已确认。
- 部署：Docker + `render.yaml`，支持 README 中的 Deploy to Render。
- 数据：无登录、无服务端数据库，用户配置和历史结果全部保存在浏览器 IndexedDB。
- 核心链路：B站输入解析、视频信息获取、字幕获取与清理、音频下载、MP3 转换、长音频切片、第一模型音频转写、第二模型文稿优化、Markdown 展示与下载、历史保存。

## 阶段 2：前端基础 UI、IndexedDB 与模型配置

目标：完成用户入口和本地数据基础，为任务流程提供配置来源。

主要任务：

1. 实现简洁低干扰的主页面：标题、输入框、开始按钮、进度条、当前阶段、日志面板、最终文稿区、中间结果折叠区、历史区、设置区。
2. 封装前端 API 调用模块，例如 `api.js`。
3. 封装 IndexedDB 模块，例如 `db.js`。
4. 设计 IndexedDB schema，保存两个模型配置和历史任务结果。
5. 实现两个独立模型配置区：音频转文字模型、文稿优化模型。
6. 支持保存 API Base URL、API Key、Model、Temperature、Stream。
7. 实现获取模型列表入口：前端调用 `POST /api/models/list`。
8. 实现历史数据导出、导入、清空和搜索的基础数据接口。
9. 确保前端不把音频文件写入 IndexedDB。

完成标准：

- 两个模型配置可以保存到 IndexedDB 并在刷新后恢复。
- 前端可以通过后端代理获取模型列表。
- API Key 仅保存在浏览器 IndexedDB，任务开始时才临时发给后端。
- 历史记录的数据结构已能保存最终文稿、字幕、AI 转写稿、日志和错误信息。
- 页面在桌面端体验清晰，移动端具备基础适配。

## 阶段 3：任务 API、状态机、日志与资源控制

目标：建立 task_id 任务机制，打通前端创建任务、轮询状态、取消任务和查看日志的最小闭环。

主要任务：

1. 实现 `POST /api/tasks` 创建任务并返回 `task_id`。
2. 实现 `GET /api/tasks/{task_id}` 返回状态、进度、阶段、日志、错误和结果。
3. 实现 `POST /api/tasks/{task_id}/cancel` 取消任务。
4. 实现任务状态：`pending`、`running`、`failed`、`completed`、`canceled`。
5. 实现阶段枚举：解析输入、获取视频信息、获取字幕、清理字幕、下载音频、转换 MP3、音频切片、切片转文字、合并转写稿、文稿优化、生成 Markdown、清理临时文件、完成。
6. 建立统一日志模块，支持 info、warning、error。
7. 建立 API Key、Authorization、Bearer token 脱敏函数，所有日志经过统一脱敏。
8. 建立按 `task_id` 隔离的临时目录管理。
9. 建立任务完成、失败、取消后的临时文件清理流程。
10. 建立资源限制：全局重任务并发默认 1，单任务音频转写并发默认 2。
11. 设计长时间无前端轮询任务的 abandoned 标记和后续清理入口。
12. 前端实现任务创建、轮询、取消、日志实时刷新和错误展示。

完成标准：

- 不接入真实 B站和模型时，也能跑通 mock 或占位任务状态流。
- 前端可以创建任务、拿到 `task_id`、轮询进度、查看日志、取消任务。
- 日志不会泄露 API Key。
- 临时目录和任务状态边界清晰。

## 阶段 4：B站输入解析、视频信息与字幕处理

目标：完成 B站单视频和当前分P的基础解析、信息获取、字幕获取与字幕清理。

主要任务：

1. 实现从普通 B站网址、完整分享文本和 BV 号中提取视频标识。
2. 使用 yt-dlp 获取视频标题、BV 号、P 序号、分P列表、时长等信息。
3. 支持普通单视频和当前分P处理。
4. 识别多P或多视频列表时，为后续多子任务预留数据结构。
5. 尽量获取 B站自带字幕，包括 UP 主上传字幕和自动字幕。
6. 字幕语言优先级：中文优先，其次英文。
7. 清理 WEBVTT 字幕：删除头、时间轴、纯数字序号、空行、NOTE、STYLE、REGION 等元信息，保留正文顺序。
8. 支持 JSON 字幕正文抽取，并按时间顺序排列。
9. 区分字幕失败原因：无字幕、超时、格式无法解析、B站返回异常、yt-dlp 或内部错误。
10. 前端在字幕失败时弹出明确提示，并允许用户选择跳过字幕继续。

完成标准：

- 完整分享文本中的 B站网址或 BV 号可以被正确识别。
- 后端可以获取单视频或当前分P的视频信息。
- 有字幕时可以得到清理后的纯文本字幕。
- 无字幕或字幕失败时，错误原因明确，并支持跳过字幕进入后续流程。
- 多P结构有清晰 TODO 或模块入口，且不会把多个视频合并成一份文稿。

## 阶段 5：音频下载、MP3 转换与切片

目标：完成后端音频处理链路，确保只处理音频临时文件，不依赖后端长期存储。

主要任务：

1. 使用 yt-dlp 只下载音频，不下载完整视频。
2. 使用安全文件名，过滤系统不允许的字符。
3. 每个任务使用独立临时目录。
4. 使用 FFmpeg 将音频统一转换为 MP3。
5. 识别需要登录权限、付费或受限内容，并给出 MVP 不支持的明确错误。
6. 对短于或等于 20 分钟的音频不切片。
7. 对超过 20 分钟的音频进行切片。
8. 切片目标长度约 20 分钟，优先在 18 到 22 分钟范围内寻找静音点。
9. 找不到静音点时按 20 分钟硬切。
10. 切片文件按 `part_001.mp3`、`part_002.mp3` 编号。
11. 日志记录切片数量、每段时长和切分位置。
12. 下载、转换、切片失败时写入明确错误和日志。

完成标准：

- 后端能下载可访问 B站视频的音频。
- 后端能把音频转换为 MP3。
- 长音频能按规则切片，并按编号输出。
- 任务完成、失败或取消后会清理临时音频目录。

## 阶段 6：第一模型音频转文字

目标：调用第一个 OpenAI-compatible Chat Completions 多模态模型，将 MP3 切片转成完整 AI 音频转文字稿。

主要任务：

1. 封装音频模型客户端模块，例如 `llm_client.py` 或 `transcription_client.py`。
2. 使用用户配置的 API Base URL、API Key、Model、Temperature、Stream。
3. 将 MP3 以常见 `input_audio` / base64 mp3 方案构造 payload。
4. 将 payload 构造放在独立函数中，方便适配不同服务商。
5. 对每个音频切片按编号调用模型。
6. 第一个片段开始后，每隔 10 秒启动下一个片段请求。
7. 单任务内片段请求并发上限默认 2。
8. 每个片段最多自动重试 3 次。
9. 区分并记录 API 超时、限流、格式错误、模型不支持音频、鉴权失败、网络错误、空内容等原因。
10. 任一片段 3 次失败后，任务失败，并向前端展示该片段失败原因。
11. 所有片段成功后，按编号顺序合并为完整 AI 音频转文字稿。
12. 合并时只做简单去重和段落修整，不额外调用模型清理每段结果。

完成标准：

- 单段 MP3 可以调用第一个模型得到文本。
- 多个切片可以并发受控地转写并按编号合并。
- 模型调用失败时错误明确，且不会泄露 API Key。
- 前端可以看到当前切片进度，例如 `part_001 / part_003`。

## 阶段 7：第二模型文稿优化与 Markdown 输出

目标：将清理后的 B站字幕和 AI 音频转文字稿合并优化为最终干净 Markdown 文稿。

主要任务：

1. 在 `prompts.py` 或等价常量文件中保存第二模型内置提示词。
2. 调用第二个 OpenAI-compatible Chat Completions 模型。
3. 输入结构包含 `<YourTask>`、`<OriginalSubtitleContent>`、`<AIAudioTranscriptionResult>`。
4. 无字幕且用户选择继续时，按需求填入“该视频没有自带字幕，请根据 AI 音频转文字的结果进行优化。”
5. 清理模型输出中的 `<think>...</think>` 内容。
6. 删除残留 `<think>`、`</think>` 标签和 `KINGFALL MODE ENABLE` 字样。
7. 最终只保留干净 Markdown 正文。
8. 生成下载文件名：`P序号_视频标题_日期时间.md`，清理非法字符，保留中文标题。
9. 前端展示最终 Markdown，并提供 `.md` 下载按钮。
10. 中间结果区域展示清理后的字幕、AI 音频转文字稿和完整日志。

完成标准：

- 第二模型可以生成最终 Markdown。
- `<think>...</think>` 内容不会展示给用户。
- 前端可以展示并下载最终 `.md` 文件。
- 中间结果可以展开查看。

## 阶段 8：历史记录、导入导出与多P基础支持

目标：补齐前端本地历史能力，并实现或预留多P任务的正确结果结构。

主要任务：

1. 完成历史任务保存：标题、原始输入、解析后网址或 BV、创建时间、最终 Markdown、清理字幕、AI 转写稿、日志、错误信息。
2. 历史记录按时间由新到旧展示。
3. 支持标题和正文搜索。
4. 支持全量导出 IndexedDB 数据为 JSON。
5. 支持从 JSON 全量导入恢复配置和历史结果。
6. 支持清空历史记录。
7. 多P或多视频任务中，一个视频或分P对应一份最终 Markdown。
8. 总任务下可包含多个子任务结果。
9. 页面按视频或分P折叠展示结果。
10. 中间结果高级区域可提供字幕 TXT、AI 转写 TXT、日志 TXT 下载。

完成标准：

- 历史记录刷新后仍可查看。
- 搜索、导出、导入、清空可用。
- 音频文件不会进入 IndexedDB。
- 多P基础结构不破坏“一个视频对应一份文稿”的规则。
