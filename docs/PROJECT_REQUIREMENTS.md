# B站视频转文字小型 Workflow / 小型 Agent 项目实现 Prompt

请你作为资深全栈工程师，帮我实现一个可以在 Windows / Mac 桌面本地运行的 B站视频转文字小型 Workflow / 小型 Agent 项目。

这个项目面向个人使用和开源本地运行场景，用户可以下载 GitHub 仓库 zip 到自己的电脑，双击启动脚本后在浏览器中打开本地网页使用。项目不需要登录系统，不需要访问密码，不需要服务端数据库，用户数据全部保存在浏览器 IndexedDB 中。

项目最终保持一个代码仓库和一套功能，不拆成两个独立版本。当前产品路线明确为 Windows / Mac 本地桌面运行，MVP 验收围绕本地 zip 启动版展开。

当前路线调整依据：

1. 普通 yt-dlp 匿名请求真实 B站公开视频时返回 `HTTP 412 Precondition Failed`。
2. 安装 `curl_cffi` 后使用 `yt-dlp --impersonate chrome` 仍返回 `HTTP 412 Precondition Failed`。
3. 使用 `yt-dlp --cookies-from-browser chrome` 在当前 Windows / Chrome 环境中返回 `Could not copy Chrome cookie database`。
4. 因此，项目主交付路径固定为本地桌面运行，并围绕本机访问能力继续推进。

本地形态：用户下载项目 zip 到 Windows 或 Mac 桌面，运行启动脚本后在本机浏览器打开 `http://127.0.0.1:8000` 使用。本地形态是推荐且优先开发的完整能力形态，优先解决 B站风控、长视频处理、FFmpeg 资源消耗和用户隐私问题。

请优先实现一个基础框架正确、流程完整、可本地启动、可排错、可逐步扩展的 MVP，不需要把所有细节一次性做到很复杂，但底层架构一定要清楚。


### 一、核心目标

用户打开前端网页后，可以把 B站视频网址、完整分享文本或 BV 号粘贴到输入框中，点击开始后，系统自动完成以下流程：

1. 从用户输入中提取真正的 B站视频网址或 BV 号。
2. 后端获取视频信息，包括标题、BV 号、P 序号、分P列表、时长等必要信息。
3. 后端获取该视频的 B站自带字幕，字幕可能来自 UP 主上传，也可能来自 B站自动字幕。
4. 后端清理 B站字幕，去除 WEBVTT 头、时间轴、空行和元信息，只保留正文文本。
5. 后端只下载该 B站视频对应的音频，不下载完整视频。
6. 后端将音频转换成 MP3 格式。
7. 如果音频较长，后端按 20 分钟左右切片，优先在 18 到 22 分钟范围内寻找静音位置切分，如果找不到合适静音点，就按 20 分钟硬切。
8. 后端调用第一个 OpenAI-compatible 模型，将 MP3 音频切片通过 Chat Completions 多模态方式转成文字。
9. 多个音频切片的转写结果按序号合并成一份完整的 AI 音频转文字稿。
10. 后端调用第二个 OpenAI-compatible 模型，把清理后的 B站字幕和 AI 音频转文字稿一起发给模型，生成最终优化后的 Markdown 文稿。
11. 前端展示最终 Markdown 文稿，用户可以下载最终文件。
12. 前端允许用户展开查看中间结果，包括清理后的 B站字幕、AI 音频转文字稿、完整日志。
13. 前端保存历史任务结果到 IndexedDB，支持搜索、导出、导入和清空。

项目只保留本地桌面 zip 启动版作为当前运行形态。README 不提供在线托管主流程，MVP 验收不包含远程构建或远程 B站读取。

9. 本地安装和下载过程需要有清楚的控制台提示，失败时给出可理解的排错建议。
10. 本地 zip 版不得要求普通用户手动复制 B站 Cookie 才能完成基础使用。


### 三、技术栈要求

后端使用 Python FastAPI。

前端已确认使用原生 HTML/CSS/JS。不要使用过重框架，优先保持项目清楚、简洁、容易修改。

后端可使用：

1. FastAPI
2. Uvicorn
3. yt-dlp，用于获取 B站视频信息、字幕和音频
4. FFmpeg，用于音频转换、静音检测和音频切片
5. httpx 或 aiohttp，用于调用 OpenAI-compatible API
6. Python 标准库，用于任务状态管理、临时文件清理、日志记录
7. curl_cffi 或 yt-dlp 支持的轻量浏览器请求指纹模拟能力，可以作为本地 B站访问的早期尝试手段，但当前真实验证显示它不能保证绕过 HTTP 412。

本地 B站访问策略应优先按以下顺序尝试：

1. 标准 yt-dlp 匿名请求。
2. 增强请求头，例如 User-Agent、Referer、Accept-Language。
3. yt-dlp 的浏览器请求指纹模拟能力，例如 `impersonate chrome` 或等价方案。
4. 针对 HTTP 412、超时、临时网络错误进行有限次数重试。
5. 如果仍失败，进入本地高级访问模式。

本地高级访问模式需要逐步评估和实现，但不得把单一方案当成可靠前提：

1. `yt-dlp --cookies-from-browser` 可作为可选能力，但当前 Windows / Chrome 已验证可能无法复制 cookie 数据库，因此不能作为唯一方案。
2. 可以评估让用户选择 Chrome、Edge、Firefox 等不同浏览器来源，但必须清楚提示成功率和失败原因。
3. 可以评估导入 `cookies.txt` 作为高级用户兜底能力，但不得放在普通用户主流程。
4. 可以评估本地专用浏览器登录窗口或本地持久浏览器 Profile 方案；如果引入 Playwright、Puppeteer、Chromium 等能力，只能用于本地版，并必须评估安装体积、启动速度和普通用户体验。
5. 任何 Cookie、浏览器 Profile 或登录态都只能保存在用户本机，不上传到第三方，不写入日志，不保存到 IndexedDB。

本地形态可以在高级模式中支持读取本机浏览器 Cookie，例如 yt-dlp 的 `cookies-from-browser` 能力，但必须遵守以下边界：

1. 默认不强制启用 Cookie。
2. 必须由用户明确选择或授权。
3. Cookie 只在本机当前任务中使用，不上传到第三方，不写入日志，不保存到 IndexedDB。
4. 本地 zip 版的主要目标是让普通用户双击脚本即可使用，Cookie 只能作为高级排错能力，不能成为普通用户理解和使用产品的前置条件。

2. API Key
3. Model
4. Temperature
5. Stream，默认开启
6. 获取模型列表按钮

第二个模型：文稿优化模型。

字段：

Authorization: Bearer {API Key}

所有日志必须自动脱敏，凡是疑似 API Key、Authorization 头、Bearer token 的内容，必须替换为 [REDACTED]。


### 七、任务机制要求

任务必须使用 task_id 机制。

前端点击开始后，向后端创建任务，后端返回 task_id，前端通过轮询读取任务状态、进度、日志、错误和结果。

建议 API：

POST /api/tasks
创建任务。

GET /api/tasks/{task_id}
读取任务状态、进度、阶段、日志、错误和结果。

POST /api/tasks/{task_id}/cancel
取消任务。

POST /api/models/list
根据用户提供的 API Base URL 和 API Key 获取模型列表。

GET /api/health
健康检查。

任务状态至少包括：

1. pending
2. running
3. failed
4. completed
5. canceled

任务阶段至少包括：

1. 解析用户输入
2. 获取视频信息
3. 获取 B站字幕
4. 清理 B站字幕
5. 下载音频
6. 转换 MP3
7. 音频切片
8. 音频切片转文字
9. 合并 AI 音频转文字稿
10. 文稿优化
11. 生成最终 Markdown
12. 清理临时文件
13. 完成

进度条需要根据阶段更新。

日志只有一个完整日志面板，像控制台一样展示所有日志，包括普通信息、警告和错误。


### 八、B站内容识别和多P处理

需要支持：

1. 普通 B站视频网址
2. 完整分享文本
3. BV 号
4. 多P视频
5. 合集或多视频列表，能识别则尽量识别

如果是单个视频，直接处理。

如果识别到多个分P或多个视频，前端要展示可处理列表，让用户选择：

1. 只处理当前分P
2. 处理多个分P或多个视频

如果用户选择多个分P或多个视频：

1. 必须一个视频对应一份最终文稿。
2. 不能把多个视频合成一份文稿。
3. 总任务下可以包含多个子任务。
4. 页面按视频或分P折叠展示结果。
5. 文稿顺序必须按照网页端视频播放顺序。

MVP 阶段如果多P识别难度较高，可以先实现普通单视频和当前分P处理，但代码结构必须预留多P子任务。


### 九、字幕获取和清理要求

后端要尽量获取 B站自带字幕。

字幕可能来自 UP 主上传，也可能来自 B站自动字幕。

如果有多种语言：

1. 默认优先中文。
2. 没有中文时使用英文。
3. MVP 可以不做用户手选语言，但内部结构要便于后续扩展。

字幕获取失败时，需要区分错误原因：

1. 没有检测到字幕
2. 获取字幕超时
3. 字幕格式无法解析
4. B站返回异常
5. yt-dlp 或内部技术错误

字幕失败后，前端要弹出明确提示，并允许用户选择跳过字幕，只用 AI 音频转文字稿继续生成最终文稿。

原始 WEBVTT 示例：

WEBVTT

00:00:00.040 --> 00:00:02.520
今天我们来聊一个最近在AI圈特别火

00:00:02.520 --> 00:00:04.380
但很多人还没真正弄懂的词

00:00:04.380 --> 00:00:05.540
Harness engineering

清理后应该变成：

今天我们来聊一个最近在AI圈特别火
但很多人还没真正弄懂的词
Harness engineering

清理规则：

1. 删除 WEBVTT 头。
2. 删除时间轴。
3. 删除纯数字序号。
4. 删除空行。
5. 删除 NOTE、STYLE、REGION 等 VTT 元信息。
6. 保留原字幕文本顺序。
7. 不要擅自改写字幕正文。
8. 如果字幕是 JSON，也要抽取正文并按时间顺序排列。


### 十、音频下载和 MP3 转换要求

后端只下载音频，不下载完整视频。

音频统一转换成 MP3。

要求：

1. 文件名使用安全文件名，去除系统不允许的字符。
2. 临时目录按 task_id 创建。
3. 每个任务有独立目录。
4. 任务完成、失败或取消后清理目录。
5. 下载错误要写入日志。
6. 如果视频需要登录权限，MVP 暂不支持，给出明确错误提示。


### 十一、音频切片要求

如果音频短于或等于 20 分钟，可以不切片。

如果音频超过 20 分钟，需要切片。

切片规则：

1. 目标长度约 20 分钟。
2. 优先在 18 到 22 分钟范围内查找静音位置。
3. 静音判断可以用 FFmpeg silencedetect 或类似方案。
4. 如果找不到静音点，就按 20 分钟硬切。
5. 切片文件必须编号，例如 part_001.mp3、part_002.mp3、part_003.mp3。
6. 后续合并文本时必须按照编号顺序合并。
7. 日志要记录切片数量、每段时长、切分位置。


### 十二、第一个模型：音频转文字

第一个模型使用 OpenAI-compatible Chat Completions 多模态方式。

要求：

1. 使用用户配置的 API Base URL、API Key、Model、Temperature、Stream。
2. 音频必须是 MP3。
3. 每个音频切片按编号转写。
4. 第一个音频片段开始后，每隔 10 秒启动下一个音频片段的模型请求。
5. 可以允许多个片段请求同时运行，但必须有并发上限，默认并发上限建议为 2，避免普通用户本机资源压力过大。
6. 每个音频片段最多自动重试 3 次。
7. 如果失败，需要判断并记录错误原因，例如 API 超时、API 限流、格式错误、模型不支持音频、鉴权失败、网络错误。
8. 如果某段 3 次都失败，任务失败，并在前端显示该段失败原因。
9. 如果全部切片成功，把所有转写结果按编号顺序合并成一份完整 AI 音频转文字稿。
10. 合并时只做简单去重和段落修整，例如上一段末尾和下一段开头出现少量重复文本时去掉重叠部分。
11. 不要调用额外模型清理每段转写结果。

音频转文字提示词使用以下内容：

# 合并文稿
你是一个专业的音频转文字校对工具，擅长核对两份来源不同的转写文本，判断哪些内容更可信，去除错误内容，保留真实内容，最终写成一篇顺序正确、内容完整、忠实原音、词语精确、阅读顺畅的音频转文字文章。

你会获得两份文稿，第一份放在 <OriginalSubtitleContent> 标签内，第二份放在 <AIAudioTranscriptionResult> 标签内。你必须同时阅读两份文稿，不能只依赖其中任何一份，也不能因为某一份来源名称看起来更可靠，就机械地认为它在所有地方都更可靠。

<OriginalSubtitleContent> 标签内放置的是音频的原字幕内容，来源通常是视频网站字幕源文件提取后的文字。它的优点是顺序通常非常可靠，基本按照视频播放顺序排列，内容覆盖也比较完整，不太容易大段遗漏。它的缺点是识别精确度可能不高，常见问题包括同音字错误、近音词错误、英文单词或缩写识别错误、专业术语识别错误、口音导致的误听、断句过碎、标点缺失、把一个词拆成多个词、把多个词误合成一个词。你要把这份内容当作顺序骨架和完整度参考，它可以帮助你确认音频内容的大体先后关系和信息覆盖范围。但你不能默认它在每一句话、每一个词语上都正确，因为它同样可能在具体词语层面出现明显误识别。

<AIAudioTranscriptionResult> 标签内放置的是 AI 模型根据音频识别得到的文字结果。它的优点是语义理解能力通常更强，能结合上下文判断某些词语真正指向的概念，对专业名词、英文表达、长句语义、上下文逻辑的判断可能更精确。它的缺点是可能出现幻觉，常见问题包括添加音频中没有出现的内容，擅自补充解释，省略某些句子，压缩原文信息，把口语化表达改写成书面总结，改变原本说话者的语气，调整原文顺序。你要把这份内容当作词语精确度和语义修正参考，但不能盲目采纳其中新增的内容。你也不能默认它在所有词语上都更准确，因为 AI 音频识别同样可能把原本正确的内容识别错、理解错或改写错。

你的核心任务是扬长避短，以 <OriginalSubtitleContent> 的顺序和完整度为主线，以 <AIAudioTranscriptionResult> 的词语精确度和语义判断为重要辅助，同时结合上下文、话题逻辑、专业常识、中文表达习惯、原音频的口语特征，综合两份文稿，生成一份更可信、更完整、更精确的最终转写稿。

你必须明确理解：在同一句话、同一个词语、同一段表达出现差异时，<OriginalSubtitleContent> 可能是正确的，<AIAudioTranscriptionResult> 也可能是正确的；<OriginalSubtitleContent> 可能是错误的，<AIAudioTranscriptionResult> 也可能是错误的。最终判断不能只看来源，必须看哪一种写法更符合上下文，哪一种写法更符合说话者正在讨论的主题，哪一种写法更符合专业领域常识，哪一种写法更像真实音频中可能说出的内容，哪一种写法能让前后语义自然成立。

你必须遵守以下工作流程：

第一步，通读 <OriginalSubtitleContent>，理解它的整体顺序、段落走向、话题变化、信息覆盖范围，把它视为最终文稿的基础骨架。

第二步，通读 <AIAudioTranscriptionResult>，理解它对同一段音频的整体识别结果，找出其中更精确的专业词、英文词、缩写、概念表达、长句语义。

第三步，按照 <OriginalSubtitleContent> 的顺序逐段核对两份文稿，判断每一处差异。如果两份文稿表达相近，但词语不同，不能自动选择某一份，必须结合上下文内容和基本常识进行判断，优先选择更符合上下文、更符合专业领域、更像说话者原意、更能使前后语义成立的表达。如果原字幕中存在明显同音字错误、英文错误、专业词错误，可以参考 AI 转写结果修正。如果 AI 转写中出现原字幕完全没有对应位置、上下文也无法证明存在的内容，应视为可能幻觉，不能写入最终文稿。

第四步，遇到两份文稿在同一句话中的核心词、关键名词、技术术语、英文表达、人名、产品名、项目名、数字、逻辑关系上发生冲突时，必须进行综合判断。判断依据包括：前后文是否反复出现同一概念，课程或文章主题是否支持该词语，行业常识中是否存在该说法，中文表达是否自然，句子内部逻辑是否通顺，后文是否引用或解释了这个词语。如果某个版本虽然来自 AI 音频识别，但明显像根据上下文补写出来的解释，不能直接采纳。如果某个版本虽然来自原字幕，但明显像同音误识别、词语断裂或专业词误听，应优先修正。

第五步，处理两份文稿都可能不完全正确的情况。如果两个版本都读起来不顺，或者都与上下文有冲突，你不能强行二选一。你可以在不添加新观点的前提下，根据上下文推断出最可能的原句表达，并采用最保守、最贴近原音、最少改动的写法。此类修正只能用于恢复原意，不能用于扩写、总结、润色或创造新内容。

第六步，处理遗漏问题。如果 <OriginalSubtitleContent> 中有某段内容，而 <AIAudioTranscriptionResult> 中缺失，通常保留原字幕对应内容，并根据上下文进行必要修正，因为 AI 转写可能发生省略。如果 <AIAudioTranscriptionResult> 中有某段内容，而 <OriginalSubtitleContent> 中完全没有相近信息，只有在它能与前后语义自然对应，且明显像原音频内容时，才可以谨慎纳入，否则应删除。

第七步，处理顺序问题。最终文稿必须遵循 <OriginalSubtitleContent> 的原始顺序，不能按照 AI 转写结果重新排列内容，不能为了让文章更像总结稿而改变原音频的信息顺序。

第八步，处理表达方式。最终文稿应保留音频转写稿的性质，尽量保留说话者原本的口语表达和讲述节奏，只做必要的错词修正、标点补充、断句整理、段落划分。不能把它改写成课程总结、读书笔记、讲义、新闻稿或宣传文案。不能额外扩写知识点，不能加入音频中没有的解释，不能把简单口语改成华丽书面语。

第九步，处理格式。最终文稿以文章形式输出，段与段之间空一行，方便阅读。不要输出原始 XML 标签，不要输出对比表，不要输出分析过程，不要输出修订说明，只输出最终整理后的转写正文。

你必须遵守以下判断规则：

1. 顺序优先参考 <OriginalSubtitleContent>，因为它通常最能反映视频播放顺序。

2. 完整度优先参考 <OriginalSubtitleContent>，因为它更不容易大段遗漏。

3. 词语精确度可以参考 <AIAudioTranscriptionResult>，尤其是专业术语、英文单词、英文缩写、产品名称、人名、项目名、技术名词、行业名词。

4. 任何单句、单词、术语、短语的最终选择，都不能只因为它来自 <OriginalSubtitleContent> 或 <AIAudioTranscriptionResult>。你必须结合上下文、专业常识、语义连贯性和真实口语可能性判断哪一版更可信。

5. 如果 <OriginalSubtitleContent> 与 <AIAudioTranscriptionResult> 在同一处表达冲突，且两者都有可能成立，应优先选择能被前后文支持、能被主题内容支持、符合常见表达习惯、逻辑更自然的一版。

6. 如果 <OriginalSubtitleContent> 的某个词语看起来像同音字、近音词、错误断词、英文误识别、专业术语误识别，应参考 <AIAudioTranscriptionResult> 和上下文进行修正。

7. 如果 <AIAudioTranscriptionResult> 的某个词语看起来像模型根据上下文自行补写、总结、解释、重组，或者改变了说话者原本的口语语气，应谨慎处理，不能盲目采纳。

8. 对于 AI 转写中新增但无法在原字幕附近找到语义依据的内容，不要采纳。

9. 对于原字幕中明显不通顺、明显与上下文矛盾、明显像误识别的内容，可以用 AI 转写结果修正，也可以结合上下文作最小幅度修正。

10. 对于两份文稿都不确定的内容，采用更保守、更贴近原字幕顺序和原音可能性的写法，避免凭空猜测。

11. 对于明显重复的字幕碎片，可以适度合并，但不能删掉有效信息。

12. 对于说话者的口头禅、轻微重复、语气词，可以适度保留，让文稿仍然像真实音频转写；如果重复严重影响阅读，可以在不改变信息的前提下轻微整理。

13. 对于标点和分段，你可以根据语义自然添加，但不能用分段改变原意。如果是中文内容，必须使用中文标点符号，绝对禁止使用英文标点符号！

14. 根据原文内容自行添加小标题，小标题使用三级标题（###）来划分。小标题必须依据原文主题自然生成，不能加入原文没有讨论的新观点。

15. 不要总结，不要缩写，不要省略，不要改写观点，不要替说话者补充观点。

16. 最终结果应尽可能做到：顺序正确，内容完整，忠实原音，词语精确，阅读清楚，段落舒适。

# 清理文稿
做到以上内容，将两段文本合并在一起之后，与此同时进行文本整理和清理，负责把真人口播稿中明显影响阅读的口水词、口癖、重复表达、断续表达和无意义过渡清理掉。

## 清理范围

请重点处理以下内容：

1. 去除明显口水词和口癖词，例如：这个、那个、就是、然后、然后的话、那、那么、的话呢、对吧、是吧、嘛、啊、呢、其实、实际上、这边的话、接下来的话、我们来看一下、我们刚才讲了等。

2. 去除没有实际信息量的过渡句，如果某句话只是讲话时的停顿、翻页、重复引导，不提供新信息，可以删除或压缩。

3. 合并同一句或相邻句中的重复表达，如果多次表达同一个意思，只保留最清楚、最完整的一次。

4. 修顺断续表达，如果原文出现说到一半改口、句子残缺、语序混乱、重复开头等情况，可以补全主语、宾语、谓语或必要的连接词，让句子变得通顺。

5. 清理无意义的自问自答，如果自问只是口播习惯，可以改成直接陈述；如果自问本身承担引出下文的作用，可以保留并适度简化。

6. 保留原文中的核心信息，包括观点、判断、例子、流程、分类、因果关系、技术名词、人物或产品名称、数字、条件和结论。

7. 保留原文的知识结构和讲解顺序，不要重新编排段落，不要把后面内容提前，不要把不同主题混在一起。

8. 可以适度补充必要的主语、宾语和过渡词，但补充内容只能用于让句子完整、顺畅，不能加入原文没有的新观点、新解释或新案例。

## 处理边界

清理后的文稿应该比原文更干净，但不能改变原文的内容重心。

如果一句话虽然啰嗦，但包含有效信息，请压缩表达，不要整句删除。

如果一个词反复出现，但在某处承担明确含义，请保留该处，不要机械删除。

如果原文存在轻微口语化表达，但不影响阅读，可以保留，不需要过度书面化。

如果原文句子本来较长，清理时尽量保持原来的句子长度和讲述节奏，不要强行拆成很多短句。

如果原文已经有清楚的段落或标题，请沿用原有结构，不要自行大幅调整。

**尊重原文稿的语言。如果原文稿是中文，那标点符号必须是中文的标点符号；如果原文稿是英文，则保持英文的标点符号。**

## 禁止事项

不要总结全文。

不要改成提纲。

不要加入外部知识。

不要纠正原文观点本身。

不要改变原文的讲述顺序。

不要删掉有效信息。

不要改变原文的整体语气。

不要为了显得更高级而大幅改写措辞。

不要把原文整理成另一篇风格完全不同的文章。

# 最终整理的格式要求
输出内容中，尽量不用破折号“——”，改用冒号“：”，因为这两个符号在日常对话的语意是几乎一致的，但破折号会让我觉得AI味很重，很不喜欢。

### 十五、错误处理要求

必须尽可能返回明确错误。

常见错误类型：

1. 用户输入无法解析。
2. B站视频不存在或无法访问。
3. 该视频需要登录权限，MVP 暂不支持。
4. 没有检测到字幕。
5. 字幕获取超时。
6. 字幕格式无法解析。
7. 音频下载失败。
8. FFmpeg 不可用。
9. MP3 转换失败。
10. 音频切片失败。
11. 模型 API Base URL 无效。
12. API Key 无效。
13. 模型列表获取失败。
14. 模型不支持音频多模态。
15. API 超时。
16. API 限流。
17. 模型返回空内容。
18. 第二模型输出格式异常。
19. 临时文件清理失败。

错误要同时显示在：

1. 当前任务状态中
2. 日志面板中
3. 任务详情中

日志中绝对不能出现完整 API Key。


### 十六、任务并发和资源限制

因为项目目标是普通用户桌面本地运行，所以要避免资源占用过高，不能假设用户电脑具备长期高负载处理能力。

要求：

1. 后端默认同一时间只运行有限数量的重任务，建议全局重任务并发上限为 1。
2. 单个任务内音频切片转写请求可以按 10 秒间隔启动，但要有并发上限，建议默认为 2。
3. 临时目录大小要尽量控制。
4. 任务完成、失败或取消后要清理临时文件。
5. 长时间没有前端轮询的任务可以标记为 abandoned，并在一段时间后清理。
6. README 中说明本地版适合个人或少量使用，不适合大量批处理；长视频处理会占用本机磁盘、CPU、内存和网络资源。


### 十七、前端任务展示要求

1. 总进度条
2. 当前阶段
3. 当前视频或分P名称
4. 如果有音频切片，显示当前切片进度，例如 part_001 / part_003
5. 日志面板实时刷新
6. 如果字幕失败，弹窗显示原因，并允许用户选择跳过字幕继续
7. 如果某个音频切片失败，显示该片段的错误原因

中间结果包括：

### 十九、代码质量要求

6. B站处理逻辑、字幕处理逻辑、音频处理逻辑、模型调用逻辑要分开。

1. 后端不能保存用户 API Key。
2. 后端不能把 API Key 写入日志。
3. 后端不能把 API Key 回传给前端。
4. 后端只临时处理当前任务音频和文本。
5. 任务完成或失败后清理临时文件。
6. 历史数据只保存在用户浏览器 IndexedDB。
7. README 要说明：清空浏览器数据可能会删除历史记录，用户应使用导出功能备份。
8. README 要说明：项目只适合处理用户有权处理的视频内容。

### 二十三、优先级

请按以下优先级实现：

第一优先级：项目能启动，前后端能通信，IndexedDB 配置能保存，任务 ID 和轮询机制能运行。

第二优先级：B站单视频字幕获取、字幕清理、音频下载、MP3 转换。

第三优先级：音频切片、第一个模型转写、合并 AI 音频转文字稿。

第四优先级：第二个模型优化、清理 <think> 内容、输出最终 Markdown。

第五优先级：历史记录、导出导入、中间结果下载、多P基础支持。

如果某些能力在当前环境很难一次完成，请先保留清楚的 TODO 和模块入口，但不要破坏整体架构。
